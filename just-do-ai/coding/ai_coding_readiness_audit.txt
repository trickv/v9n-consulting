# AI Coding Readiness Audit

You are auditing this codebase for **AI coding readiness**: the infrastructure that makes AI-assisted development safe and fast at team scale.

Without these layers, AI-assisted development gives you AI-speed typing with human-speed verification — which is slower than what you had before. The audit names the gaps so they can be closed.

## What to assess

For each layer below, determine whether it is **present**, **partial**, or **missing**, and write a one-line finding explaining what you found (or didn't).

1. **Continuous integration.** Automated checks that run on every push or pull request. This is where the checks below get enforced — if it's missing, say so here, once.
2. **Local verification loop.** From a fresh checkout, can a developer — or an agent — install dependencies and run the checks with documented commands? This is how an agent verifies its own work before handing it back. Look for lockfiles, pinned runtime versions (`.nvmrc`, `.tool-versions`, a devcontainer), a task runner (`Makefile`, `justfile`, `package.json` scripts), pre-commit hooks, and commands documented in the `README` or `AGENTS.md`/`CLAUDE.md`.
3. **Automated tests.** Tests that exist *and* run automatically, from CI or a hook. Tests that nothing runs automatically are **partial** at best.
4. **Static analysis.** Linting, formatting, and type checking where the language allows it. Say which of the three are in place.
5. **Security scanning.** Automated detection of vulnerable dependencies and committed secrets, with config kept out of the code (e.g. `.env` gitignored, an `.env.example` committed).
6. **AI-assisted code review.** Independent automated review of pull requests (e.g. CodeRabbit, Copilot, Cubic, or similar).
7. **Deployment automation.** A defined path from merged code to a deployable artifact or environment, visible from this repo — ideally an artifact built once and promoted as-is. The deployment *target* may live in a separate infra repo — assess what's wired up from here.
8. **Observability.** Error tracking, logging, or monitoring wired into the code (e.g. Sentry, Datadog, OpenTelemetry). Structured logging to stdout for the platform to collect counts — don't mark this missing just because there's no vendor SDK. Detected by imports and configuration; runtime health is out of scope.

When a gap is really another layer's gap — tests exist but there's no CI to run them — mark it **partial** and point to that layer rather than repeating its next move.

Use your judgment about where to look. Conventional config files, CI directories, dependency manifests, and `README` files are all fair game. Don't ask the user for access to external systems — assess what's visible in the repo. If the repo holds several apps or packages, assess it as a whole and call out any that differ significantly.

## How to report

Produce a single markdown file named `AI_CODING_READINESS.md` at the repo root with the following structure:

```
# AI Coding Readiness Audit

**Audited:** <date>
**Codebase:** <brief one-line description of what this is>

## Summary

<2-3 sentences: overall state, biggest gaps, what stood out>

## Status

| Layer | Status |
| --- | --- |
| Continuous integration | ✅ Present / 🟡 Partial / ❌ Missing |
| Local verification loop | ... |
| Automated tests | ... |
| Static analysis | ... |
| Security scanning | ... |
| AI-assisted code review | ... |
| Deployment automation | ... |
| Observability | ... |

One row per layer, in the order listed above. One emoji + one word per row, nothing else. Use ❓ Unknown only if a layer genuinely couldn't be assessed.

## Findings

<one section per layer, in the order listed above>

### <Layer name> — <Present | Partial | Missing | Unknown>

**Found:** <what you observed>
**Why it matters:** <one sentence on the cost of this gap, if any>
**Next move:** <one concrete smallest-useful step to close or improve this layer>
```

## Tone

Write findings the way a senior engineer would write them for another senior engineer: direct, specific, no hedging. If something is missing, say it's missing. If something is half-built, say what's half about it. Skip the encouragement language.

## Constraints

- One pass, read-only: don't install dependencies, run builds, or run tests.
- Don't modify any files except creating `AI_CODING_READINESS.md`.
- If you genuinely can't tell whether a layer is present after a reasonable look, mark it **Unknown** and say what you'd need to check to be sure. This applies especially to tools often enabled outside the repo — AI review bots installed as GitHub Apps, Dependabot alerts or secret scanning turned on in repository settings — where no trace in the repo means **Unknown**, not **Missing**.
